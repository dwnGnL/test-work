# Сервис приёма платежей в USDT: дизайн-документ

**Термины и допущения.** Счёт — запрос партнёра на оплату, у него свой депозитный адрес; платёж — один входящий перевод USDT на этот адрес; сбор — перевод зачисленных USDT с депозитного адреса на основной кошелёк. Счёт выставляется в USDT и живёт 60 минут.

## 1.1. Архитектура

Модульный монолит на Go и PostgreSQL: каждый компонент — модуль со своими таблицами и интерфейсом, чужие таблицы он не трогает. Фоновые задачи берут работу из таблиц-очередей в той же базе, поэтому смена статуса, проводки и событие для вебхука пишутся одной транзакцией. Схема взаимосвязи — в [architecture.md](architecture.md).

| Компонент | Ответственность |
|---|---|
| API | Счета, статусы, баланс; партнёр по API-ключу; идемпотентность по `(партнёр, ключ)` |
| Сканер блоков | Читает блоки подряд, находит платежи, следит за порогом и реоргами |
| Обработчик платежей | Ведёт платёж: порог подтверждений → AML → зачисление или возврат |
| AML-клиент | Провайдер за интерфейсом, повторы при сбоях, ответ хранится для аудита |
| Ledger | Двойная запись, только добавление; единственное место, где меняются балансы |
| Возвраты и сбор | Готовят исходящие транзакции: возврат и сбор только зачисленных сумм |
| Подписант | Отдельный процесс с ключами; подписывает только операции из базы, в пределах лимитов |
| Вебхуки | Доставляют партнёрам события из таблицы outbox |
| Админка | Лента счёта по шагам, ручной AML-разбор, отправка возврата; действия журналируются |

**Обнаружение.** Источник истины — собственное сканирование блоков через RPC двух провайдеров: из каждого блока берём события `Transfer` контракта USDT (`eth_getLogs` по хэшу блока) и ищем получателя среди наших адресов. Подписка по WebSocket теряет события при обрыве, поэтому только будит сканер; внешний индексер служит для сверки: в учёте денег на чужую корректность не опираемся.

- **Курсор.** Номера и хэши обработанных блоков хранятся в базе до их финализации; после простоя сканер продолжает с последнего.
- **Подтверждения.** Партнёр видит платёж как `detected` с первого блока, деньги двигаются после порога. Порог по умолчанию — финализация блока (≈15 минут): её откат стоил бы атакующему трети стейка сети. Партнёру можно задать N блоков (как в коде Части 2); тогда возможен реорг после зачисления (1.2).
- **Реорг.** `parent_hash` нового блока не совпал с сохранённым — находим общего предка по сохранённым хэшам, платежи выброшенных блоков помечаем `orphaned`, читаем заново; расхождение глубже финализации — стоп и алерт. Ключ платежа — `(tx_hash, позиция события в receipt.logs)`, блок — изменяемый атрибут (решение 2).
- **Поддельный токен.** Принимаем события только с адреса контракта USDT из конфига; имя и символ не читаем. Контракт умеет переехать на новый адрес (флаг `deprecated`): за флагом следим.
- **Неуспешная транзакция.** Читаем события, а не входные данные: отменённая транзакция событий не оставляет. Нулевые переводы игнорируем.

**Адреса и ключи.** Один адрес на счёт: платёж однозначно сопоставляется со счётом. В v1 адреса выводятся из HD-кошелька: API знает только публичный ключ (xpub); seed зашифрован ключом KMS и расшифровывается только в памяти подписанта. В проде — контракты-форвардеры (CREATE2): адрес вычисляется заранее, приватного ключа у него нет; ключ основного кошелька — в HSM. Основной кошелёк горячий с лимитом остатка, излишек — на холодном мультисиге.

**Вебхуки.** Гарантия — «хотя бы один раз»: повторы с растущим интервалом в течение 72 часов. Порядок не гарантируем: в событии есть `event_id` для дедупликации и полное состояние счёта с номером версии, устаревшее партнёр отбрасывает. Подпись — HMAC-SHA256 от `timestamp.body` секретом партнёра, `timestamp` — время попытки; окно в 5 минут защищает от повтора перехваченного события.

**1 млн счетов в день** — около 12 в секунду, API и база справятся. Первым ломается сбор средств в сети: миллион сборов по 60–100 тыс. газа — порядка 15–20% пропускной способности всего Ethereum, и цена газа вырастет от нашей же нагрузки. Лечим сбором по порогу суммы, пакетами через форвардеры и сетями с дешёвым газом. Затем — рост таблиц (≈10 млн строк в сутки: секционирование, хранимый баланс, отчёты с реплики) и лимиты AML-провайдера (кэш по адресу отправителя, второй провайдер).

## 1.2. Деньги

```
Платёж:  detected ─порог─▶ aml_pending ─низкий риск─▶ credited
           ▲ │                  ├─высокий риск─▶ rejected (создан возврат)
    заново │ ▼ реорг            └─средний риск─▶ manual_review ─▶ credited | rejected
         orphaned ◀─ реорг после порога (режим N) — из любого статуса
Возврат: created ─▶ ready_to_send ─оператор (v1)─▶ broadcast ─▶ confirmed
         created ─▶ awaiting_address (биржа) ─адрес прошёл AML─▶ ready_to_send
         ready_to_send ⇄ deferred (газ ≥ суммы);  created ─▶ blocked (санкции, заморозка)
         broadcast: не в блоке — повтор с тем же nonce; отменена в блоке ─▶ ready_to_send
```

Пока AML недоступен, платёж остаётся в `aml_pending`: проверка повторяется с растущим интервалом, через 30 минут срабатывает алерт, решения по таймауту нет. Статус счёта выводится из суммы платежей в `credited`: `pending → partially_paid → paid`; `expired` — срок вышел (по времени блока), сумма не набрана и платежей в обработке нет. Переплата и оплата после срока зачисляются с признаками `overpaid` и `late`.

**Ledger-счета:** `assets:deposits` (USDT на депозитных адресах), `hold:aml` (ждёт решения AML), `partner:{id}`, `refunds:payable` (к возврату отправителям), `revenue:fees`, `revenue:gas_recovery` (удержанный газ). Пример: платёж 100 USDT, комиссия 1,5%, газ возврата 3 USDT.

| Шаг | Событие | Дебет | Кредит | USDT |
|---|---|---|---|---|
| 1 | Платёж прошёл порог | `assets:deposits` | `hold:aml` | 100.000000 |
| 2a | AML: низкий риск | `hold:aml` | `partner:{id}` | 98.500000 |
| | | `hold:aml` | `revenue:fees` | 1.500000 |
| 2b | AML: высокий риск | `hold:aml` | `refunds:payable` | 100.000000 |
| 3 | Возврат `confirmed` | `refunds:payable` | `assets:deposits` | 97.000000 |
| | | `refunds:payable` | `revenue:gas_recovery` | 3.000000 |

Обычный платёж — шаги 1 и 2a; на AML-проверке — только шаг 1; возврат — 1, 2b, 3.

- До порога проводок нет, поэтому реорг не оставляет висящих денег. После порога (режим N) — сторно с новым ключом, отмена неотправленного возврата, алерт, возможный минус на балансе партнёра.
- Статус меняется условным обновлением (`WHERE status = прежний`) в одной транзакции с проводкой. Ключ проводки `{payment_id}:{шаг}` (2a и 2b — один шаг) передаётся в ledger при каждом вызове, ключ возврата — `payment_id`; оба уникальны (решение 3).
- Суммы — целые числа в минимальных единицах (10⁻⁶ USDT). Ставка в базисных пунктах копируется в счёт при создании; процент считается в целых, `(amount × bps + 5000) / 10000`, минимум — по 1.3.3; `net = amount − fee`.
- Сверка раз в сутки: по каждой валюте сумма по ledger — ноль; активы в ledger равны балансам в сети с поправкой на платежи в `detected` и возвраты в `broadcast`.

**Газ для возврата.** В v1 газовый кошелёк переводит на депозитный адрес ETH на одну транзакцию, после её подтверждения с адреса уходит USDT. Цель — форвардеры: ETH на адресе не нужен, транзакцию оплачивает основной кошелёк. В обоих случаях расход несёт отправитель: стоимость газа в USDT по курсу на момент отправки удерживается из суммы. Иначе платил бы сервис, и газовый кошелёк можно было бы опустошить потоком копеечных «грязных» переводов; партнёр тоже не виноват. Расход ETH ведём в ledger отдельной валютой, курсовая разница на сервисе. Газ при сборе обычных платежей сервис оплачивает из своей комиссии (1.3.3).

## 1.3. Продуктовые вопросы

**1. Недоплата 3%.** Клиент видит на странице партнёра: «получено 97 из 100 USDT, доплатите 3 на тот же адрес до 14:30». Партнёр видит `partially_paid`, недостачу, получает вебхук и решает сам: ждать доплату, принять как есть или вернуть клиенту (в v1 — оператор с баланса партнёра, газ из суммы); полученное за вычетом комиссии уже на его балансе. Поддержка отвечает по ленте счёта на «я заплатил, а заказ не оплачен». Настраивается на партнёра: допустимая недоплата (по умолчанию 1 USDT, решение 6), в её пределах счёт сразу `paid`.

**2. AML отклонил платёж.** Партнёр получает вебхук `rejected` и сам пишет клиенту. За возврат платит отправитель (1.2). Сумма не покрывает газ — не возвращаем: она остаётся обязательством на `refunds:payable`, а не нашим доходом. Из `deferred` возврат выходит при дешёвом газе или по запросу отправителя, подписанному с адреса. Отправитель — биржа: автовозврат ушёл бы на её общий кошелёк и не дошёл до клиента, поэтому возврат ждёт в `awaiting_address`, пока клиент через партнёра не сообщит адрес. В обоих ожиданиях через 90 дней без обращения решает комплаенс. При санкционном совпадении или заморозке адреса Tether возврат `blocked`, отчёт регулятору.

**3. Комиссия.** Процент со ставкой на партнёра и минимум на счёт: газ сбора платится за адрес, а не за перевод, и на мелких счетах съедает процент. Минимум считается нарастающим итогом, чтобы его не обойти дроблением: `fee = max(ставка × получено по счёту, минимум) − уже взято`, не больше платежа. Чисто фиксированная комиссия душит мелкие платежи. Тарифы по обороту — позже. В ledger комиссия — отдельная строка в момент зачисления; при возврате комиссии нет, только газ. В отчёте у платежа три суммы: получено, комиссия, зачислено.

**4. Метрики.** Партнёру:

- конверсия счетов в оплату и причины неоплаты (недоплата, срок, AML) — его главный показатель денег;
- оборот, комиссия, зачисления за период и баланс — для сверки с его учётом;
- время от обнаружения перевода до зачисления (медиана, p95) — когда отдавать товар;
- доставка вебхуков (доля успешных, застрявшие) — без неё товар не отдан.

Внутренней команде:

- расхождение ledger с балансами в сети — сохранность денег, должно быть ноль;
- отставание сканера и возраст незавершённых платежей и возвратов — первый признак, что деньги встали;
- доступность AML и доля высокого риска по партнёрам — всплеск означает грязный трафик;
- доход с комиссии против расхода на газ по партнёрам — кто из них убыточен.

**5. Две недели, два разработчика.** Выпускаем: API счетов и баланса, сканер с реоргами, AML с повторами, ledger со сверкой, подписанные вебхуки, возврат до `ready_to_send`, ручки оператора (лента счёта, AML-разбор, возврат, выплаты и сбор, заведение партнёра), алерты на отставание сканера и расхождение ledger с сетью. Откладываем: кабинеты (пока API и выгрузки), автоматические выплаты и сбор, форвардеры, тарифы, API возврата для партнёра, вторую сеть. Принцип: автоматизируем приём и учёт, где ошибка тихо искажает деньги; переводы наружу на малых объёмах — вручную.

## 1.4. Журнал решений

1. **Порог зачисления по умолчанию — финализация, а не N блоков.** N даёт вероятность, финализация — экономическую гарантию. Цена — 15 минут ожидания, поэтому N оставили настройкой на партнёра.
2. **Ключ платежа не включает блок.** Отвергли `(block_hash, log_index)` и `(tx_hash, log_index)`: `log_index` — номер события в блоке, а не в транзакции, и после реорга та же транзакция выглядела бы новым платежом.
3. **Один ключ на решение по платежу (передумали).** Сначала у зачисления и возврата были разные ключи проводок: защита от повтора одного шага. Сценарий «два воркера получили разные ответы AML» показал, что проходят обе проводки и одни 100 USDT уходят и партнёру, и отправителю. Теперь это один шаг с одним ключом и условной сменой статуса.
4. **Возврат уходит с депозитного адреса.** Отвергли сведение всех депозитов на основной кошелёк с возвратом оттуда: «грязные» монеты смешались бы с чистыми, и биржи стали бы задерживать выплаты с него. Цена — отдельный путь возврата и его газ (1.2).
5. **Зачисляем каждый чистый платёж, статус счёта производный.** Отвергли строгое совпадение суммы (поток возвратов из-за комиссий бирж) и холд до полной оплаты (таймеры и автовозвраты).
6. **Допуск недоплаты — сумма, а не процент (передумали).** Сначала взяли 1% от счёта. Посчитали и передумали: комиссия вывода у биржи фиксированная, на счёте в 20 USDT процент её не покрывает, а на счёте в 10 000 прощает лишние 100.
7. **Модульный монолит, а не микросервисы.** Отвергли микросервисы с брокером: двум разработчикам это лишняя инфраструктура, а атомарность «статус + проводка + событие» проще в одной базе. Вынос оставили дешёвым: свои таблицы у каждого модуля и вызовы, идемпотентные по ключу, — у ledger, сканера или вебхуков сменится транспорт, а не логика. До этого растём инстансами воркеров.
