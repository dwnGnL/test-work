# Сервис приёма платежей в USDT: дизайн-документ

**Термины.** Счёт — запрос партнёра на оплату со своим депозитным адресом и сроком 60 минут; платёж — один входящий перевод USDT на этот адрес; сбор — перевод зачисленных USDT с депозитного адреса на основной кошелёк.

## 1.1. Архитектура

Модульный монолит на Go и PostgreSQL: у каждого модуля свои таблицы и интерфейс. Очереди фоновых задач лежат в той же базе, поэтому статус, проводки и событие для вебхука пишутся одной транзакцией. Схема — в [architecture.md](architecture.md).

| Компонент | Ответственность |
|---|---|
| API | Счета, статусы, баланс; вход по API-ключу; идемпотентность по `(партнёр, ключ)` |
| Сканер блоков | Читает блоки подряд, находит платежи, следит за порогом и реоргами |
| Обработчик платежей | Ведёт платёж: порог → AML → зачисление или возврат |
| AML-клиент | Провайдер за интерфейсом, повторы при сбоях, ответ хранится для аудита |
| Ledger | Двойная запись, только добавление; единственное место, где меняются балансы |
| Возвраты и сбор | Готовят исходящие транзакции |
| Подписант | Отдельный процесс с ключами; подписывает только операции из базы |
| Вебхуки | Доставляют партнёрам события из outbox |
| Админка | Лента счёта, ручной AML-разбор, отправка возврата |

**Обнаружение.** Сами сканируем блоки через RPC двух провайдеров: берём события `Transfer` контракта USDT по хэшу блока и ищем получателя среди наших адресов. Подписка теряет события при обрыве и только будит сканер; внешний индексер служит для сверки, не для учёта.

- **Курсор.** Номера и хэши обработанных блоков лежат в базе; после простоя сканер продолжает с последнего.
- **Подтверждения.** Платёж виден как `detected` с первого блока, деньги двигаются после порога: по умолчанию это финализация блока (≈15 минут), партнёру можно задать N блоков (так в коде Части 2).
- **Реорг.** `parent_hash` нового блока не совпал с сохранённым — находим общего предка, платежи выброшенных блоков помечаем `orphaned`, читаем заново. Ключ платежа — `(tx_hash, номер события)` без блока: транзакция, включённая заново, оживляет ту же запись.
- **Поддельный токен и неуспешная транзакция.** Принимаем события только с адреса контракта USDT из конфига, имя и символ не читаем. Читаем события, а не входные данные: отменённая транзакция событий не оставляет.

**Адреса и ключи.** Один адрес на счёт: платёж однозначно сопоставляется со счётом. В v1 адреса выводятся из HD-кошелька: API знает только публичный ключ, seed зашифрован в KMS и открывается только в памяти подписанта. В проде — контракты-форвардеры (CREATE2): адрес вычисляется заранее, ключа у него нет. Основной кошелёк горячий с лимитом, излишек — на холодном мультисиге.

**Вебхуки.** Доставка «хотя бы один раз», повторы с растущим интервалом в течение 72 часов. В событии есть `event_id` для дедупликации и состояние счёта с номером версии: порядок не гарантируем. Подпись — HMAC-SHA256 от времени попытки и тела секретом партнёра; окно в 5 минут защищает от повтора перехваченного события.

**1 млн счетов в день** — около 12 в секунду, API и база справятся. Первым ломается сбор средств в сети: миллион сборов — порядка 15–20% пропускной способности Ethereum. Лечим сбором по порогу суммы, пакетами через форвардеры и сетями с дешёвым газом.

## 1.2. Деньги

```
Платёж:  detected ─порог─▶ aml_pending ─низкий риск─▶ credited
           ▲ │                  ├─высокий риск─▶ rejected (создан возврат)
    заново │ ▼ реорг            └─средний риск─▶ manual_review ─▶ credited | rejected
         orphaned ◀─ реорг после порога (режим N) — из любого статуса
Возврат: created ─▶ ready_to_send ─оператор (v1)─▶ broadcast ─▶ confirmed
         created ─▶ awaiting_address (биржа) ─адрес прошёл AML─▶ ready_to_send
         ready_to_send ⇄ deferred (газ ≥ суммы);  created ─▶ blocked (санкции, заморозка)
         broadcast: не в блоке — повтор с тем же nonce; отменена в блоке ─▶ ready_to_send
```

Пока AML недоступен, платёж ждёт в `aml_pending`, проверка повторяется, решения по таймауту нет. Статус счёта выводится из суммы зачисленных платежей: `pending → partially_paid → paid`; `expired` — срок вышел, сумма не набрана, платежей в обработке нет.

**Ledger** — журнал двойной записи: операция — это проводка с нулевой суммой строк, баланс счёта — сумма его строк. Он показывает, сколько денег у сервиса лежит физически и кому сколько из них причитается. Счета: `assets:deposits` и `assets:hot_wallet` (USDT на депозитных адресах и основном кошельке), `hold:aml` (ждёт AML), `partner:{id}` и `refunds:payable` (долг перед партнёром и отправителями), `revenue:fees`, `revenue:gas_recovery`. Пример: платёж 100 USDT, комиссия 1,5%, газ возврата 3 USDT.

| Шаг | Событие | Дебет | Кредит | USDT |
|---|---|---|---|---|
| 1 | Платёж прошёл порог | `assets:deposits` | `hold:aml` | 100.000000 |
| 2a | AML: низкий риск | `hold:aml` | `partner:{id}` | 98.500000 |
| | | `hold:aml` | `revenue:fees` | 1.500000 |
| 2b | AML: высокий риск | `hold:aml` | `refunds:payable` | 100.000000 |
| 3 | Возврат `confirmed` | `refunds:payable` | `assets:deposits` | 97.000000 |
| | | `refunds:payable` | `revenue:gas_recovery` | 3.000000 |
| 4 | Сбор на основной кошелёк | `assets:hot_wallet` | `assets:deposits` | 100.000000 |
| 5 | Выплата партнёру | `partner:{id}` | `assets:hot_wallet` | 98.500000 |

Обычный платёж — шаги 1 и 2a; на AML-проверке — только шаг 1; возврат — 1, 2b, 3. После шагов 4 и 5 на основном кошельке остаётся комиссия, 1,5 USDT.

- До порога проводок нет, поэтому реорг не оставляет висящих денег. После порога (режим N) — сторно, алерт и возможный минус на балансе партнёра.
- Статус меняется условно (`WHERE status = прежний`) в одной транзакции с проводкой. Ключ проводки `{payment_id}:{шаг}` уникален, зачисление и возврат — один шаг (решение 1).
- Суммы — целые в минимальных единицах (10⁻⁶ USDT). Ставка копируется в счёт при создании; комиссия `(amount × bps + 5000) / 10000`, партнёру — остаток.

**Сверка с внешним миром.** Ledger — наше представление о деньгах, настоящие остатки лежат снаружи. Расхождение — алерт и остановка исходящих операций.

| Снаружи | В ledger | Что сверяем |
|---|---|---|
| Сеть: USDT на наших адресах | `assets:deposits`, `assets:hot_wallet` | Остатки на финализированном блоке раз в сутки и после сбора и выплат, с поправкой на платежи до порога и транзакции в пути |
| Сеть: ETH газового кошелька | `assets:gas_wallet`, `expense:gas` | Так же; газ ведётся отдельной валютой |
| AML-провайдер | Платежи `credited` и `rejected` | У каждого решённого платежа сохранён ответ |

Внутри журнала: сумма по каждой валюте равна нулю, у платежа в итоговом статусе есть проводка.

**Газ для возврата.** В v1 газовый кошелёк переводит на депозитный адрес ETH на одну транзакцию, затем с адреса уходит USDT; цель — форвардеры, где платит основной кошелёк. Расход несёт отправитель: стоимость газа удерживается из суммы. Плати сервис — газовый кошелёк можно опустошить потоком копеечных «грязных» переводов. Газ сбора обычных платежей идёт из комиссии.

## 1.3. Продуктовые вопросы

**1. Недоплата 3%.** Клиент видит на странице партнёра: «получено 97 из 100 USDT, доплатите 3 на тот же адрес до 14:30». Партнёр видит `partially_paid` и недостачу, получает вебхук и решает сам: ждать доплату, принять как есть или вернуть через оператора; полученное за вычетом комиссии уже на его балансе. Поддержка отвечает по ленте счёта. На партнёра настраивается допустимая недоплата (по умолчанию 1 USDT, решение 4): в её пределах счёт сразу `paid`.

**2. AML отклонил платёж.** Партнёр получает вебхук `rejected` и сам пишет клиенту. За возврат платит отправитель (1.2). Сумма не покрывает газ — не возвращаем (`deferred`): она остаётся долгом на `refunds:payable`, а не доходом, и ждёт дешёвого газа или запроса отправителя, подписанного с адреса. Отправитель — биржа: возврат ушёл бы на её общий кошелёк и не дошёл до клиента, поэтому ждём адрес от клиента (`awaiting_address`). Через 90 дней без обращения решает комплаенс. Санкционное совпадение или заморозка адреса Tether — блокировка и отчёт регулятору вместо возврата.

**3. Комиссия.** Процент со ставкой на партнёра и минимум на счёт: газ сбора платится за адрес и на мелких счетах съедает процент. Минимум считается нарастающим итогом по счёту, иначе его обходят дроблением платежа. Чисто фиксированная комиссия душит мелкие платежи; тарифы по обороту — позже. В ledger комиссия — отдельная строка при зачислении, в отчёте у платежа три суммы: получено, комиссия, зачислено.

**4. Метрики.** Партнёру: конверсия счетов в оплату с причинами неоплаты (недоплата, срок, AML) — его главный показатель денег; оборот, комиссия, зачисления и баланс — для сверки с его учётом; время от обнаружения перевода до зачисления — когда отдавать товар. Внутренней команде: расхождение ledger с остатками в сети — сохранность денег, должно быть ноль; отставание сканера и возраст незавершённых платежей и возвратов — первый признак, что деньги встали; доступность AML и доля высокого риска по партнёрам — всплеск означает грязный трафик.

**5. Две недели, два разработчика.** Выпускаем: API счетов и баланса, сканер с реоргами, AML с повторами, ledger со сверкой, подписанные вебхуки, возврат до `ready_to_send`, ручки оператора, алерты на отставание сканера и расхождение с сетью. Откладываем: кабинеты, автоматические выплаты и сбор, форвардеры, тарифы, вторую сеть. Принцип: автоматизируем приём и учёт, где ошибка тихо искажает деньги; переводы наружу на малых объёмах — вручную.

## 1.4. Журнал решений

1. **Один ключ на решение по платежу (передумали).** Сначала у зачисления и возврата были разные ключи проводок. Сценарий «два воркера получили разные ответы AML» показал, что проходят обе: одни 100 USDT уходят и партнёру, и отправителю. Теперь это один шаг с одним ключом и условной сменой статуса.
2. **Возврат уходит с депозитного адреса.** Отвергли сведение всех депозитов на основной кошелёк с возвратом оттуда: «грязные» монеты смешались бы с чистыми, и биржи стали бы задерживать наши выплаты. Цена — отдельный путь возврата и его газ.
3. **Зачисляем каждый чистый платёж, статус счёта производный.** Отвергли строгое совпадение суммы (поток возвратов из-за комиссий бирж) и холд до полной оплаты (таймеры и автовозвраты).
4. **Допуск недоплаты — сумма, а не процент (передумали).** Сначала взяли 1% от счёта. Посчитали: комиссия вывода у биржи фиксированная, на счёте в 20 USDT процент её не покрывает, а на счёте в 10 000 прощает лишние 100.
5. **Модульный монолит, а не микросервисы.** Двум разработчикам брокер и сервисы — лишняя инфраструктура, а атомарность «статус + проводка + событие» проще в одной базе. Вынос оставили дешёвым: свои таблицы у модуля и вызовы, идемпотентные по ключу. До этого растём инстансами воркеров.
