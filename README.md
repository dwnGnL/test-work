# Сервис приёма платежей в USDT

Тестовое задание Senior Backend Engineer (Go). Сервис принимает платежи в USDT (ERC-20) для
партнёров: партнёр создаёт счёт, клиент переводит USDT на депозитный адрес, сервис ждёт
подтверждений, проверяет отправителя в AML и либо зачисляет деньги партнёру за вычетом
комиссии, либо создаёт возврат.

- **Часть 1, дизайн-документ:** [docs/design.md](docs/design.md), схема компонентов —
  [docs/architecture.md](docs/architecture.md).
- **Часть 2, код:** этот репозиторий. Сеть и AML заменены симулятором и моком за интерфейсами.

## Запуск

```bash
docker compose up --build
```

- API слушает на `http://127.0.0.1:18080`. Порт меняется переменной `APP_PORT`, порт базы на
  хосте — `DB_PORT` (по умолчанию 55432).
- Миграции применяются при старте.
- Заведены два демо-партнёра:

| Партнёр | API-ключ | Комиссия |
|---|---|---|
| alpha | `demo-key-alpha` | 1,5% |
| beta | `demo-key-beta` | 0,5% |

- Порог подтверждений N = 3. Сканер блоков и обработчик платежей работают в фоне раз в секунду.
- Адрес из чёрного списка AML: `0x000000000000000000000000000000000000dead`.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | локальный Postgres | Строка подключения |
| `HTTP_ADDR` | `:8080` | Адрес HTTP-сервера внутри контейнера |
| `CONFIRMATIONS` | `3` | Порог подтверждений N |
| `INVOICE_TTL` | `60m` | Срок жизни счёта |
| `SCAN_INTERVAL` | `1s` | Период фоновых проходов сканера и обработчика |
| `AML_BLACKLIST` | пусто (в compose — адрес `…dead`) | Адреса высокого риска через запятую |
| `USDT_CONTRACT` | адрес USDT в Ethereum | События других токенов игнорируются |
| `DEMO_SEED` | `false` (в compose `true`) | Создать демо-партнёров |
| `SIM_API` | `false` (в compose `true`) | Включить ручки симулятора `/sim/*` |

## Сценарий руками

Команды рассчитаны на запущенный `docker compose up`. Фоновые задачи работают раз в секунду,
поэтому после блоков стоит подождать секунду-две, прежде чем смотреть счёт.

Один раз задать переменные и короткие обёртки над `curl`:

```bash
API=http://127.0.0.1:18080
KEY='Authorization: Bearer demo-key-alpha'
CLEAN=0x1111111111111111111111111111111111111111
DIRTY=0x000000000000000000000000000000000000dead

# new_invoice <ключ идемпотентности> <сумма>: создаёт счёт, запоминает его номер и адрес
new_invoice() {
  RESP=$(curl -s -X POST $API/v1/invoices -H "$KEY" -H "Idempotency-Key: $1" -d "{\"amount\":\"$2\"}")
  ID=$(echo "$RESP" | sed -E 's/.*"id":"([^"]+)".*/\1/')
  ADDR=$(echo "$RESP" | sed -E 's/.*"deposit_address":"([^"]+)".*/\1/')
  echo "$RESP"
}
pay()     { curl -s -X POST $API/sim/transfers -d "{\"to\":\"$ADDR\",\"from\":\"$1\",\"amount\":\"$2\"}"; echo; }
blocks()  { curl -s -X POST $API/sim/blocks -d "{\"count\":$1}"; echo; }
invoice() { curl -s $API/v1/invoices/$ID -H "$KEY"; echo; }
balance() { curl -s $API/v1/balance -H "$KEY"; echo; }
```

### 1. Обычный платёж

```bash
new_invoice order-1 100      # счёт на 100 USDT: статус pending, есть deposit_address
pay $CLEAN 100               # «клиент» переводит 100 USDT
blocks 1                     # перевод попал в блок
invoice                      # платёж detected, счёт pending
balance                      # 0.000000: до порога и AML партнёр ничего не получает
blocks 2                     # три подтверждения
invoice                      # платёж credited, счёт paid, amount_received 100.000000
balance                      # 98.500000: 100 минус комиссия 1,5%
```

Между `blocks 2` и `invoice` платёж проходит статус `aml_pending`.

### 2. Идемпотентность и изоляция партнёров

```bash
# тот же ключ и та же сумма: код 200 и тот же счёт
curl -s -o /dev/null -w '%{http_code}\n' -X POST $API/v1/invoices -H "$KEY" -H 'Idempotency-Key: order-1' -d '{"amount":"100"}'
# тот же ключ, другая сумма: 422
curl -s -w ' %{http_code}\n' -X POST $API/v1/invoices -H "$KEY" -H 'Idempotency-Key: order-1' -d '{"amount":"101"}'
# другой партнёр не видит счёт: 404
curl -s -w ' %{http_code}\n' $API/v1/invoices/$ID -H 'Authorization: Bearer demo-key-beta'
# и у него свой баланс
curl -s $API/v1/balance -H 'Authorization: Bearer demo-key-beta'; echo
```

### 3. Высокий риск: возврат

```bash
new_invoice order-2 100
pay $DIRTY 100               # отправитель из чёрного списка AML
blocks 3
invoice                      # платёж rejected, у него refund в статусе ready_to_send на 100
balance                      # не изменился
```

### 4. AML недоступен

```bash
curl -s -X POST $API/sim/aml -d '{"available":false}'; echo
new_invoice order-3 50
pay $CLEAN 50
blocks 3
invoice                      # платёж aml_pending, сколько ни ждать
balance                      # не изменился: деньги в холде
curl -s -X POST $API/sim/aml -d '{"available":true}'; echo
invoice                      # через несколько секунд платёж credited
```

Пауза между попытками растёт: 5 с, 10 с, 20 с и так далее до 5 минут. Если AML был выключен
долго, после включения придётся подождать очередную попытку.

### 5. Реорг до набора подтверждений

```bash
new_invoice order-4 30
pay $CLEAN 30
blocks 1
invoice                      # платёж detected
curl -s -X POST $API/sim/reorg -d '{"depth":1,"drop_transfers":false}'; echo
invoice                      # платёж orphaned, проводок по нему нет
blocks 1
invoice                      # тот же платёж снова detected, второго не появилось
blocks 2
invoice                      # credited, зачислен один раз
```

С `"drop_transfers":true` транзакция исчезает совсем: платёж остаётся `orphaned`, сколько бы
блоков ни прошло.

### 6. Недоплата и доплата

```bash
new_invoice order-5 100
pay $CLEAN 60
blocks 3
invoice                      # счёт partially_paid, получено 60
pay $CLEAN 40
blocks 3
invoice                      # счёт paid, два платежа
```

### 7. Рестарт

В любой момент любого сценария можно выполнить `docker compose restart app`. Сервис продолжит
с того же места: курсор сканера и состояние платежей лежат в базе, а блоки, добытые за время
простоя, будут прочитаны.

## Тесты

```bash
make test
```

Команда поднимает базу из compose и запускает `go test -race ./...`. Нужны Go 1.25 и Docker;
на Linux детектору гонок нужен `gcc`. Каждый тест создаёт себе временную базу. В тестах нет
ожиданий по таймеру: сканер и обработчик вызываются напрямую, время подменяется.

## Как устроен код

Модульный монолит: модуль — это пакет Go и своя схема PostgreSQL.

| Пакет | Схема | Что делает |
|---|---|---|
| `internal/partners` | `partners` | Партнёры, вход по API-ключу (в базе только sha256 ключа) |
| `internal/invoices` | `invoices` | Счета: идемпотентное создание, депозитный адрес, статус |
| `internal/chain` | `chainsim` | Интерфейс сети и симулятор: переводы, блоки, реорг |
| `internal/scanner` | `scanner` | Чтение блоков, курсор, обработка реорга |
| `internal/payments` | `payments` | Платёж и его статусы, решение после AML |
| `internal/aml` | нет | Интерфейс проверки и мок с чёрным списком |
| `internal/ledger` | `ledger` | Двойная запись, идемпотентные проводки, балансы |
| `internal/refunds` | `refunds` | Возврат, один на платёж |
| `internal/httpapi` | нет | HTTP: счета, баланс, ручки симулятора |
| `internal/money` | нет | Суммы целыми числами, комиссия |
| `internal/platform/postgres` | нет | Пул соединений, транзакции, миграции |
| `internal/config` | нет | Конфигурация из переменных окружения |
| `internal/e2e` | нет | Сквозные тесты всего сценария через HTTP |
| `cmd/server` | нет | Сборка сервиса и два фоновых цикла |

Правила, которые соблюдены во всех модулях:

- SQL модуля лежит только в его `store.go` и обращается только к своей схеме. Чужие данные —
  через функции другого пакета. Внешних ключей между схемами нет.
- Запись, которая должна быть атомарной с чужой записью, принимает транзакцию вызывающего:
  статус платежа, проводка и возврат фиксируются вместе.
- Суммы — целые числа в минимальных единицах (10⁻⁶ USDT), в JSON — строками. Float нет нигде.
- Паник в коде нет, всё возвращается ошибкой.

### Путь платежа

| Статус | Что произошло | Проводка |
|---|---|---|
| `detected` | Перевод замечен в блоке | нет |
| `orphaned` | Блок откатился до набора подтверждений | нет |
| `aml_pending` | Набрано N подтверждений | `assets:deposits` → `hold:aml`, вся сумма |
| `credited` | AML: низкий риск | `hold:aml` → `partner:{id}` (сумма − комиссия) и `revenue:fees` (комиссия) |
| `rejected` | AML: высокий риск, создан возврат | `hold:aml` → `refunds:payable`, вся сумма |

До набора подтверждений проводок нет, поэтому реорг не оставляет висящих денег.

### Почему перевод не зачисляется дважды

- **Платёж уникален** по паре «хэш транзакции + номер события». Блок в ключ не входит:
  транзакция, включённая заново после реорга, оживляет ту же запись.
- **Статус меняется условно** (`WHERE status = прежний`): из двух обработчиков решение
  принимает тот, у кого строка действительно изменилась.
- **Проводка идемпотентна по ключу** `{payment_id}:{шаг}`. Зачисление и возврат — один шаг с
  одним ключом, провести оба нельзя, даже если два обработчика получили разные ответы AML.
- **База страхует код:** сумма проводки обязана быть нулевой, журнал только на добавление,
  зачисление возможно только с вердиктом AML, возврат уникален по платежу.

## Допущения и упрощения

Условие намеренно содержит пробелы. Ниже решения, которые я принял, и то, что упростил в коде.

**Сумма и счёт**

- Каждый чистый платёж зачисляется партнёру, статус счёта выводится из полученной суммы:
  `pending`, `partially_paid`, `paid`, `expired`. Недоплата, доплата вторым платежом и
  переплата обрабатываются одинаково, отдельной логики нет.
- Допуск недоплаты на партнёра, признаки `overpaid` и `late` описаны в документе, в коде их нет.
- Срок счёта сравнивается с часами сервиса, а не со временем блока: у блоков симулятора
  времени нет. Платёж после срока всё равно зачисляется.
- Верхней границы суммы счёта нет.

**Комиссия**

- Ставка в базисных пунктах копируется из партнёра в счёт при создании и из счёта в платёж:
  смена ставки не задевает выставленные счета.
- Округление до ближайшего, половина вверх, в целых числах. Сумма партнёру — вычитанием.
- Минимальная комиссия на счёт описана в документе, в коде только процент.

**Сеть**

- Порог — N блоков из конфига. В документе по умолчанию финализация, N — настройка партнёра.
- Реорг глубже порога в коде не обрабатывается: платёж не трогается, в лог пишется ошибка.
  Платёж, уже ждущий AML, в этом случае будет зачислен, хотя перевода в сети нет. В документе
  описано, как должно быть: сторнирующие проводки и долг партнёра.
- Симулятор хранит состояние в базе, чтобы «сеть» переживала рестарт сервиса.
- Таблица обработанных блоков сканера не чистится.

**AML и возвраты**

- У AML два исхода. Ручная проверка, заморозка при санкционном совпадении и возврат на адрес
  биржи описаны в документе.
- Возврат доводится до статуса `ready_to_send` на полную сумму. Отправки, газа и удержания
  его стоимости в коде нет, поэтому ledger одновалютный и счёта `revenue:gas_recovery` нет.
- Проверки AML в пачке идут по очереди: до 20 платежей за проход, 3 секунды на вызов.
- Выключатель мока AML хранится в памяти процесса.

**Доступ и безопасность**

- Один статический ключ на партнёра, без ротации, срока и ограничения частоты запросов. TLS нет.
- Демо-ключи публичны. `DEMO_SEED` и `SIM_API` включены только в compose, порты открыты
  только на localhost. Ручки `/sim/*` работают без входа.
- Депозитный адрес случайный, закрытого ключа к нему нет.
- Сервис подключается к базе ролью-владельцем. В проде нужна отдельная роль без права
  отключать триггеры ledger.

**Чего нет по условию:** UI, вебхуков, реальных адресов, работы с Ethereum и отправки транзакций.

## Как я использовал AI

Работал с Claude Code на всех этапах.

**Для чего**

- Разбор условия: список пробелов, из которого я выбрал те, что влияют на код и документ.
- Дизайн-документ: черновик, затем пять проверок разными «ролями» (соответствие условию,
  факты про Ethereum, проводки и статусы, продуктовые ответы, вычитка).
- Код: по этапам, каждый этап отдельными коммитами. После этапа я разбирал код, задавал
  вопросы и менял то, с чем не согласен.
- Ревью каждого этапа отдельным проходом, которому поручалось не доверять зелёным тестам и
  доказывать дефекты пробами. Правки по ревью шли отдельными коммитами `fix:`.
- Мутационная проверка тестов: защита временно убирается, тест обязан упасть.

**Что решал сам**

- Что считать оплатой счёта и что отложить в документ (заморозка, реорг после порога).
- Модульный монолит со своими таблицами у каждого модуля вместо отдельного сервиса ledger.
- Ошибки вместо паник, SQL в `store.go`, вставка строк проводки одним запросом, порядок
  объявлений в файлах.

**Где AI ошибся и как это заметили**

| Ошибка | Как заметили |
|---|---|
| У зачисления и возврата были разные ключи проводок: при разных ответах AML прошли бы обе | Проверка сценариев по документу |
| Сканер держал блокировку на отдельном соединении: при его обрыве второй экземпляр работал параллельно с первым, и платёж попадал в холд раньше порога | Ревью с заданием искать гонки, воспроизведено тестом |
| Порог подтверждений считался от головы сети без повторной проверки: платёж из выброшенного блока проходил порог | То же ревью, воспроизведено тестом |
| Вызов AML без таймаута: зависший провайдер останавливал весь обработчик. Мок не зависает, тесты этого не видели | Ревью, проба с зависшим провайдером |
| Схема ledger позволяла дописать вторую пару проводок в существующую транзакцию и очистить журнал через `TRUNCATE` | Ревью, проверено на живой базе |
| Статус счёта мог сравниваться с суммой после комиссии: счёт на 100 при зачисленных 98,5 остался бы частично оплаченным | Ревью |
| Паника в расчёте комиссии и в конструкторах проводок: в фоновом обработчике она роняла бы сервис | Заметил при разборе кода |
| SQL вперемешку с логикой, вставка строк циклом, константы в середине файла | Заметил при разборе кода |
| Допуск недоплаты в процентах не покрывал фиксированную комиссию биржи | Проверка продуктовых ответов |
| В журнале решений причина «передумали» противоречила самому документу | Первая проверка документа |

Главный вывод для себя: зелёные тесты, даже с мутационной проверкой, показывают только то, о
чём подумал автор тестов. Обе гонки в сканере нашёл отдельный проход, которому было поручено
искать порядки событий, а не подтверждать готовое.
